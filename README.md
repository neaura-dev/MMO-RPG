## 1. Описание проекта

MMO-RPG - учебная модель игровой системы. Проект включает иерархию
игровых юнитов, фабрики для создания персонажей, игровое поле для их
хранения и итератор для обхода занятых клеток.

Различные типы юнитов работают через общий базовый интерфейс. Игровое
поле хранит объекты через `std::unique_ptr`, что выражает уникальное
владение и обеспечивает автоматическое освобождение памяти. Отдельное
внимание уделено глубокому копированию поля, перемещению ресурсов и
демонстрации этих возможностей в `main.cpp`.

## 2. Цель и задачи

### Цель

Разработать объектно-ориентированную модель игровой системы на C++,
применив наследование, полиморфизм, паттерны проектирования, итераторы и
средства управления ресурсами.

### Задачи

- разработать иерархию игровых юнитов;
- реализовать фабрики для создания семейств персонажей;
- создать игровое поле для хранения юнитов;
- реализовать итератор для последовательного обхода персонажей на поле;
- обеспечить глубокое копирование и перемещение поля;
- продемонстрировать 3 сценария в `main.cpp`;
- проверить сборку и корректность ключевых сценариев.

## 3. Архитектура

### 3.1. Иерархия юнитов

`Unit` задаёт общий интерфейс юнита. Производные классы
`Knight`, `Archer` и `Mage` представляют основные роли. Конкретные
персонажи относятся к семействам `Kingdom Guardian`, `Forest Keeper` и
`Undead`: `Paladin`, `CrossbowMan`, `Cleric`, `Ent`, `Centaur`, `Druid`,
`Skeleton`, `ShadowArcher` и `Necromancer`.

Общий интерфейс позволяет хранить и обрабатывать объекты разных
производных типов единообразно.

### 3.2. Фабрики

`UnitFactory` задаёт интерфейс создания юнитов разных ролей. Конкретные
фабрики `KingdomGuardianFactory`, `ForestKeeperFactory` и
`UndeadFactory` создают персонажей соответствующих семейств. Благодаря
этому код, заполняющий поле, не обязан самостоятельно создавать каждый
конкретный класс.

### 3.3. Игровое поле

`GameField` отвечает за хранение и размещение персонажей. Для хранения
используется `std::vector<std::unique_ptr<Unit>>`. Пустой указатель
может соответствовать свободной клетке, поэтому операции доступа и
обхода должны учитывать пустые элементы.

### 3.4. Итератор

Итератор игрового поля предоставляет операции начала и завершения
обхода, перехода к следующему элементу и доступа к текущему юниту. Он
скрывает детали внутреннего контейнера. Если реализация пропускает
пустые элементы, клиентский код получает последовательность существующих
юнитов.

## 4. Паттерны проектирования

### 4.1. Абстрактная фабрика (Abstract Factory)

**Назначение:** предоставить общий интерфейс для создания семейств
связанных объектов, скрывая конкретные классы создаваемых объектов.

В проекте `UnitFactory` задаёт операции создания персонажей разных
ролей, а `KingdomGuardianFactory`, `ForestKeeperFactory` и
`UndeadFactory` создают конкретные семейства юнитов.

**Обоснование выбора:** создание объектов отделено от кода, который
использует их на игровом поле. Для выбора другого семейства можно
заменить конкретную фабрику, не переписывая логику хранения юнитов.

Участники паттерна:
- абстрактная фабрика: `UnitFactory`;
- конкретные фабрики: `KingdomGuardianFactory`, `ForestKeeperFactory`,
`UndeadFactory`;
- продукты: классы персонажей и их базовые интерфейсы.

### 4.2. Итератор (Iterator)

**Назначение:** предоставить последовательный доступ к элементам
коллекции, не раскрывая детали её внутреннего устройства.

Итератор игрового поля позволяет обходить юнитов с помощью `begin()`,
`end()`, `operator++` и `operator*`. Сравнение итераторов позволяет
определить завершение обхода. Обработка пустых клеток реализуется
логикой перехода к следующему допустимому элементу.

## 5. Управление памятью и копирование

### 5.1. `std::unique_ptr`

`std::unique_ptr<Unit>` выражает уникальное владение объектом. Указатель
нельзя копировать, но владение можно передать, например с помощью
`std::move`. При уничтожении владельца объект автоматически
освобождается. Это помогает избегать ручного управления через `new` и
`delete`.

### 5.2. Глубокое копирование

Копирование контейнера с `std::unique_ptr` напрямую невозможно. Для
глубокого копирования необходимо создать новые объекты юнитов. В проекте
для этого используется виртуальный метод `clone()`, который создаёт
копию соответствующего динамического типа.

### 5.3. Перемещение

Перемещение позволяет передать ресурсы объекту-получателю без
необходимости создавать независимые копии всех юнитов. Для передачи
используется семантика перемещения C++, в частности `std::move`.

### 5.4. Правило пяти

Правило пяти относится к деструктору, конструктору копирования,
оператору копирующего присваивания, конструктору перемещения и оператору
перемещающего присваивания.

При ручном управлении ресурсами эти операции могут требовать
согласованной реализации. Если класс использует RAII-типы стандартной
библиотеки, часть операций может быть сгенерирована компилятором. Однако
`std::unique_ptr` не копируется, поэтому глубокое копирование
`GameField` необходимо реализовать отдельно, если оно поддерживается
классом.

## 6. Демонстрационные сценарии

### 6.1. Создание поля и заполнение через фабрики

**Цель:** продемонстрировать создание поля и использование нескольких
фабрик.

1.  Создать `GameField`.
2.  Создать фабрики разных семейств.
3.  Создать несколько юнитов.
4.  Передать их игровому полю.
5.  Вывести содержимое поля и характеристики персонажей.

**Ожидаемый результат:** поле содержит созданных юнитов, которые
доступны через общий интерфейс.

### 6.2. Глубокое копирование и перемещение

**Цель:** проверить независимость копии и показать перемещение ресурсов.

1.  Создать и заполнить исходное поле.
2.  Скопировать поле.
3.  Убедиться, что соответствующие юниты являются разными объектами.
4.  Изменить здоровье юнита в копии.
5.  Проверить, что оригинал не изменился.
6.  Переместить копию в другой объект и вывести его содержимое.

**Ожидаемый результат:** копия содержит независимые объекты, а
перемещённое поле получает переданные ресурсы.

### 6.3. Обход итератором и массовая операция

**Цель:** продемонстрировать обход юнитов и применение операции ко всем
найденным персонажам.

1.  Создать поле с несколькими юнитами и свободными клетками.
2.  Выполнить обход от `begin()` до `end()`.
3.  Вывести характеристики каждого юнита.
4.  Выполнить массовую операцию, например уменьшение здоровья.
5.  При наличии корректно поддерживаемого интерфейса продемонстрировать
    удаление юнита во время обхода.

**Ожидаемый результат:** итератор позволяет обращаться к существующим
юнитам, а массовая операция изменяет объекты поля.

## 8. Сборка и запуск

### Требования

- C++-компилятор с поддержкой используемого стандарта;
- CMake;
- совместимая система сборки.

Из корневой директории проекта выполните:

``` bash
cmake -S . -B build
cmake --build build
```

Расположение исполняемого файла зависит от генератора CMake и
конфигурации сборки. В Windows при использовании Visual Studio он может
находиться в `build/Debug/`. Ориентируйтесь на вывод сборки.

Запустите исполняемый файл и убедитесь, что все демонстрационные
сценарии из `main.cpp` выполняются.

## 10. Заключение

В проекте реализована объектно-ориентированная модель игровой системы с
иерархией юнитов, фабриками и игровым полем. Используются полиморфизм,
паттерны Abstract Factory и Iterator, а также `std::unique_ptr` для
управления владением динамическими объектами.

Глубокое копирование позволяет создавать независимую копию поля, а
перемещение передавать ресурсы без обязательного копирования всех
персонажей. Демонстрационные сценарии предназначены для проверки
создания юнитов, независимости копии, перемещения ресурсов и обхода поля
итератором.
